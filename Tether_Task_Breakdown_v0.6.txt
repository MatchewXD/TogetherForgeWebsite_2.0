# **1\. How this document works**

The website task board is controlled only by staff. Contributors claim a Ready Small (or a Ready Medium that has no Smalls) and follow the exact steps listed. They cannot edit task structure. When every step under a Small is done and the output exists, the task goes to review. Credit is awarded only after staff accept the work.

This file is the source of truth for what belongs on the board. Do not paste the entire game into the live board in one shot. Import Staff Only plus the first Ready lane first. Keep later epics visible as locked chapters so people can see the path without claiming work that would break the prototype.

* Do the steps in order. Check a box only when that step is fully finished.

* If something is unclear or blocked, leave a comment recommending a change. Do not invent new scope.

* Off-brief work is declined even if the craft is good. Cite the Canon doc it missed.

* Staff Only tasks are visible. Volunteers cannot claim them.

* Blocked tasks are visible. They become Ready only when staff flip the state after the blocker is gone.

## **Definition of Done**

A Small is complete only when every listed step is done, the stated output exists (file, map, note, or playable behavior), and staff have accepted the review. A Medium is complete when all of its Smalls are complete. Points and public credit are awarded at acceptance, not at self-check.

# **3\. Board states and skill tags**

Every task on the live board must have exactly one state and at least one skill tag.

| State | Meaning | Claimable? |
| :---- | :---- | :---- |
| Staff Only | Founder or staff work. Visible so the community can see the spine. | No |
| Blocked | Real work, waiting on a named blocker (usually another task or a playtest). | No |
| Ready | Unblocked, exact steps, output path, Definition of Done, theme constraint. | Yes |
| In Review | Submitted. Waiting on staff. | No |
| Done | Accepted. Credit awarded. | No |

Skill tags: Programming, Art, Audio, Level, Docs, QA, Community. Size tags: First Spark, Small, Medium.

A Ready task always includes: one-sentence goal, ordered steps, output path, theme constraint (which Canon doc to match), and how to turn it in (PR against develop, or upload plus comment).

# **4\. How new work gets on the board**

Contributors never add tasks. They can only recommend a change in a comment, a playtest note, or an Idea.

* Intake: task comment, playtest note, Ideas page, or staff finding a gap.

* Staff triage: Accept (write a Small, set Ready or Blocked), Park (later epic), or Reject (already covered, off theme, or too vague).

* Accepted work still waits its turn. Epic 2 can spawn new Smalls after a playtest. The Ready lane stays short on purpose.

# **7\. EPIC 1 — Project foundation**

**Staff Only.** Owner: founder / Together Forge staff. No public gameplay work starts until this epic is Done.

Purpose: one engine version, one repo, one folder map, and a Canon packet so later tasks have a target.

## **Medium 1.1 — Engine lock and empty project**

State: Staff Only. Output: a Tether Unreal project that opens on 5.8.x with no errors, plus Docs/EngineDecision.md.

### **Small 1.1.1 — Record the engine decision**

* Create Docs/EngineDecision.md.

* State the lock: Unreal Engine 5.8.x, current 5.8 patch from the Epic Games Launcher.

* Write why: last planned UE5 major, Chaos physics for the tether, production-ready Iris for later multiplayer, one install target for contributors. UE6 is not the start version.

* List four project requirements the engine must meet: stable constraint/physics for a shared tether, multiplayer path we can reuse on later TF games, workable low-poly / modular art pipeline, free editor for volunteer contributors under Epic’s terms.

* Staff sign-off in the same file. This Small is done only after sign-off is recorded.

### **Small 1.1.2 — Install and create the project**

* Install Unreal Engine 5.8.x (current patch) from the Epic Games Launcher.

* Create a new Blueprint project named Tether. Blank or Third Person is fine. Record the template used.

* Set project settings so the saved engine association matches 5.8.x.

* Create the Content/Tether folder tree listed in section 5\.

* Create an empty map Content/Tether/Maps/TetherPrototype and set it as the editor startup map.

* Save a note in Docs/EngineDecision.md: exact engine version string, template, and that the project opens without errors.

## **Medium 1.2 — GitHub and collaboration base**

State: Staff Only. Output: private GitHub repo with branch rules, LFS, Unreal gitignore, and a README a new contributor can follow.

### **Small 1.2.1 — Repository**

* Create a private GitHub repository for Tether under the Together Forge account or organization.

* Add the official Unreal Engine .gitignore (Binaries, DerivedDataCache, Intermediate, Saved, .vs, and local user files).

* Enable Git LFS. Track uasset, umap, uasset types plus common art binaries (png, wav, fbx, and similar) in .gitattributes. Do not put source .cpp/.h/.md on LFS.

* First commit: Initial project setup — Tether.

* Create develop from main. Protect main. Require pull requests into develop and main.

* Write the repo URL into Docs/Repo.md. Do not put live secrets in the repo.

### **Small 1.2.2 — README and CONTRIBUTING**

* README.md must contain: project name, one-sentence description, required Unreal version, how to open the project, how to run TetherPrototype, and the default branch.

* CONTRIBUTING.md must contain: claim a Ready task on togetherforge.net first, use Tether-X.Y.Z in the PR title, branch from develop, do not invent scope, leave a comment if blocked, staff review before merge.

* Add a PR template that requires Task ID, what changed, and which Canon doc the work follows.

* Add a short access rule: repo access is granted after a claimed repo task is approved.

* Commit both files. Medium 1.2 is done when both Smalls are checked and a second machine can clone and open the project.

## **Medium 1.3 — Canon packet**

State: Staff Only to write. Public to read once published. Output: four short markdown files in Docs/. These are the documents Conduct review and art review cite until the website Vision library exists.

### **Small 1.3.1 — Vision and What this is not**

* Write Docs/Vision.md: one page. What Tether is (two players bound by a shared line, cooperating to move resources and survive stress on that line), who it is for, and the feeling of play.

* Write Docs/WhatThisIsNot.md: no single-hero power fantasy, no real-world party marks or current political movement branding in assets or official copy, no invented factions or slogans outside Canon, no scope added because it would be cool.

* Both files stay short enough that a moderator can reread them before a review.

### **Small 1.3.2 — Style lock and Tether rules**

* Write Docs/StyleLock.md: palette direction (muted industrial plus one energy accent), silhouette rules, material language, and scale notes (door height, player height, resource size). Mark it Draft until staff approve a lock.

* Write Docs/TetherRules.txt: starting numbers only (max distance band 8–12 units, tension bands Low / Medium / High). Label unknowns as Open. Epic 2 will overwrite this file after playtests. Later systems must read this file instead of inventing rules.

* Link all four Canon files from README.md.

# **9\. EPIC 2 — Core tether physics**

**Staff Only / trusted group.** Highest design risk. Do not move later gameplay epics to Ready until at least two people have playtested this and Docs/TetherRules.txt has been updated.

Purpose: prove the shared tether feels good, is readable, and creates decisions. Exact numbers are discovered here.

## **Medium 2.1 — Basic tether between two pawns**

State: Staff Only. Output: TetherPrototype with two stand-ins linked by a visible line that respects a max distance.

### **Small 2.1.1 — Player stand-ins**

* Create a simple pawn or character in Content/Tether/Characters/BP\_PlayerStandIn.

* Basic movement with WASD or left stick. Confirm two instances can move independently before the tether exists.

* Place two instances in TetherPrototype.

### **Small 2.1.2 — Distance constraint and visual**

* Create a tether actor or component in Content/Tether/Tether/ that takes two targets.

* Start max distance in the 8–12 unit band. Write the number into Docs/TetherRules.txt.

* Apply a spring or constraint that pulls them back past max distance. Use Chaos / built-in constraints. Do not add a custom physics engine.

* Draw a line that always connects both pawns. Change color or intensity near max stretch.

* Play and confirm: free movement inside the limit, pull-back outside it, line always visible.

### **Small 2.1.3 — Local dual control**

* One keyboard can drive Player A with WASD and Player B with arrow keys (or an equivalent split).

* Document controls in Docs/Controls.md.

* Done when one person can test tether behavior without a second machine.

## **Medium 2.2 — Tension states**

State: Staff Only. Output: Low / Medium / High tension readable by a spectator.

* Small 2.2.1 — Compute stretch as a percent of max distance. Default bands: Low 0–50%, Medium 50–85%, High 85–100%. Write thresholds in TetherRules.txt and expose the state.

* Small 2.2.2 — High tension reduces max move speed by a documented multiplier. Optional light momentum transfer when one pawn stops short.

* Small 2.2.3 — Visual and a placeholder High-tension audio cue. A spectator can tell the state from visuals alone.

## **Medium 2.3 — Over-stretch and recovery**

State: Staff Only. Output: documented behavior at 100%+ stretch plus a recovery path. Tether is never permanently lost in normal play.

* Small 2.3.1 — Decide and document what happens at over-stretch (soft break, drain, forced slow, or brief disconnect). Implement it. Distinct cue. Write the rule in TetherRules.txt.

* Small 2.3.2 — Automatic or player-triggered recovery. Test the full cycle. Medium 2.3 is done only after a two-person playtest using Docs/qa/PlaytestNote.md.

# **10\. EPIC 3 — Tether-aware movement**

State: Blocked until Epic 2 playtest passes. Purpose: movement that still respects the line.

* Medium 3.1 — Walk, run, jump, ground detect, keyboard and gamepad. Document speeds. Camera: third-person that tries to keep both pawns readable, or first-person plus a HUD tether cue. Write the choice in Docs/.

* Medium 3.2 — Active pull toward partner. Optional resist. Failure tests: one falls off a ledge, both jump, one sprints while the other stands. Fix the worst issues before the Medium is Done.

# **11\. EPIC 4 — Resources and warp**

State: Blocked until Epic 3 is stable. Purpose: the loop that turns motion into colony support.

* Medium 4.1 — ResourceNode prefab, interact volume, carry limit 1 or 2, deliberate drop. Place at least six nodes in the prototype or a test map.

* Medium 4.2 — Checkpoint transfers carried resources to a session total, clears carry, plays a placeholder confirm. Show the running total. Done when collect → carry → warp → total updates.

# **12\. EPIC 5 — Enemies that stress the tether**

State: Blocked until the Epic 4 loop works. Purpose: threats whose job is coordination, not a DPS sponge.

* Medium 5.1 — Latch enemy moves toward a pawn or the tether midpoint, attaches, applies a documented penalty (extra tension, slow, or drain), and shows a clear attached state.

* Removal is faster when both players use Energy Pulse inside a short window. Playtest with two people and confirm the pair advantage is obvious.

# **13\. EPIC 6 — First playable surface level**

State: Blocked until Epic 5 has one working enemy. Purpose: one full loop that can be shown.

* Medium 6.1 — At least five modular graybox pieces in Content/Tether/Modular. Build Level\_01\_Surface: start, two traversal sections, resources, one or two enemy points, end checkpoint. Walk it with the tether on.

* Medium 6.2 — Two players collect, handle one enemy, warp, see the colony total and a simple complete message. Record a short note or video. That recording is the Definition of Done for the first playable loop.

# **14\. EPIC 7 and 8 — After the slice**

State: Parked until Epic 6 is playtested. Do not expand into full Small checklists yet.

* Epic 8 — Authored station sequence. Short zero-g or broken corridor to a generator. Creature drive-off in 2–3 coordination phases. Success is positioning and tool use, not a large health bar.
